Design only. I haven't applied anything to Supabase, and I haven't inspected the live project, so I don't know whether it already has tables.

One change from the approved plan: **I'm dropping the `carts` table.** A single `cart_items` keyed by `user_id` is enough because there is one cart per user. A header table would add a join and a policy for no gain.

## Conventions
- Money is `integer` cents (`*_cents`). It's never a float or `numeric`, and formatting happens in the UI.
- Primary keys are `uuid default gen_random_uuid()`. The exceptions are `categories` (slug) and `orders` (also gets a readable number).
- Every table has `enable row level security`. Client roles get only the grants they need: `revoke all` first, then `grant select` or whatever each policy needs.
- Policies use `(select auth.uid())` rather than bare `auth.uid()`, so Postgres evaluates it once per query instead of once per row.

## Tables

**`categories`**: `slug text pk`, `name text not null`, `sort_order int`
- RLS: `select` for `anon, authenticated` using `true`. No write policies, so writes come only from the service-role seed script.

**`products`**
- `id`, `slug text unique not null`, `title`, `brand`, `description`, `features text[]`
- `category_slug → categories` (restrict), `price_cents int check (>0)`, `list_price_cents int null` (the strikethrough price)
- `stock int not null check (stock >= 0)`
- `rating_avg numeric(2,1)`, `rating_count int` (denormalized)
- `is_active bool default true`, `created_at`
- `search tsvector generated always as (to_tsvector('english', title || ' ' || coalesce(brand,'') || ' ' || coalesce(description,''))) stored`
- Indexes: GIN on `search`; btree on `(category_slug, price_cents)`; btree on `(category_slug, rating_avg desc)`; unique on `slug`.
- RLS: `select` using `is_active`. No client writes. The `stock >= 0` check constraint is the last line of defense against overselling.

**`product_images`**: `id`, `product_id → products on delete cascade`, `path text` (Storage path), `position int`, `unique(product_id, position)`
- Index: `(product_id, position)`.
- RLS: public `select`, no client writes.

**`reviews`** (seeded and read-only): `id`, `product_id → products cascade`, `author_name text`, `rating int check (1..5)`, `title`, `body`, `created_at`
- No `user_id`, since nobody can write reviews in the MVP.
- Index: `(product_id, created_at desc)`.
- RLS: public `select`, no client writes.

**`cart_items`**: `user_id → auth.users cascade`, `product_id → products cascade`, `quantity int check (1..10)`, `updated_at`, `primary key (user_id, product_id)`
- The composite pk gives upsert semantics and makes `user_id` the leading index column.
- RLS: one `for all` policy with `using (user_id = (select auth.uid()))` and the same expression in `with check`. Users can only touch their own rows. Anon has no grant.
- It stores no price. Cart prices are always read live from `products`.

**`addresses`**: `id`, `user_id → auth.users cascade`, `full_name`, `line1`, `line2`, `city`, `region`, `postal_code`, `country`, `phone`, `is_default bool`
- Partial unique index on `(user_id) where is_default`, so there's at most one default per user.
- RLS: `for all` with `user_id = (select auth.uid())`, in both `using` and `with check`.

**`orders`**
- `id uuid pk`, `order_number bigint generated always as identity (start 100001)` (unique, shown to the user)
- `user_id → auth.users on delete set null`, `status text default 'placed' check (...)`
- `subtotal_cents`, `shipping_cents`, `tax_cents`, `total_cents`, all `int not null`, with a check that `total = subtotal + shipping + tax`
- `shipping_address jsonb not null` (a snapshot), `payment_method text default 'mock'`, `created_at`
- Index: `(user_id, created_at desc)`.
- RLS: `select` using `user_id = (select auth.uid())`. There is no insert, update or delete policy and no grant, so clients cannot create orders directly. Rows come only from the `place_order` RPC.

**`order_items`**
- `id`, `order_id → orders cascade`, `user_id` (denormalized so the policy is a plain column check with no subquery)
- `product_id → products on delete set null`, `title_snapshot`, `image_path_snapshot`, `unit_price_cents int`, `quantity int`
- Index: `(order_id)`.
- RLS: `select` using `user_id = (select auth.uid())`. No client writes.

**Storage:** a public `product-images` bucket. Anyone can read. Only the service role writes, so there are no storage policies for client roles.

## Cart storage decision

**Guest cart:** `localStorage` holds `[{product_id, qty}]`, with no prices and no product data. The UI hydrates it by fetching the current products. This is anon-readable and needs no server state.

**Logged-in cart:** the `cart_items` table is the source of truth. It follows the user across devices and is the only cart `place_order` reads.

**Merge on login:** a `merge_cart(items jsonb)` RPC (security invoker, so RLS applies) upserts the guest items into `cart_items`. It clamps quantity to 10 and skips inactive products. The client clears `localStorage` after success.

**Why not the alternatives:**
- Server-side guest carts need an anonymous identity and a cleanup job for abandoned rows. That's more machinery for a feature the MVP doesn't need.
- A cookie-only cart for everyone would break cross-device persistence and make the RPC trust client data.

## Price snapshot decision

- `orders` and `order_items` copy everything the user saw: the unit price, the title, the image path, and the shipping address as `jsonb`. Later price changes, renamed products, or deleted addresses must never rewrite history.
- `product_id` is `on delete set null`, so history survives product deletion. The link is informational only (for "Buy it again").
- Totals are stored, not recomputed. The check constraint keeps them internally consistent.

**`place_order(address_id uuid, expected_total_cents int)`** is `security definer` with `set search_path = ''`. It takes `auth.uid()` from the session and does the following in one transaction:
1. Reads `cart_items` joined to `products` itself. It trusts no client-supplied prices or quantities.
2. Locks the product rows (`for update`), validates `is_active` and stock, and decrements stock.
3. Computes totals server-side. Shipping is a flat rule and tax is zero.
4. Raises if the computed total differs from `expected_total_cents`, so the user never pays a price they didn't see.
5. Inserts the order and items with the snapshots, deletes the cart rows, and returns the order id.

## Where I'm unsure
1. **Price-drift handling.** Failing on a total mismatch is correct but blunt. A friendlier flow would return the new totals and ask the user to confirm. I'd start with the hard fail.
2. **Merge conflict rule.** If the same product is in the guest cart and the DB cart, I'd sum (clamped to 10). Taking the max is arguably more intuitive. This is a judgment call, not a technical one.
3. **Anonymous auth as an alternative.** Supabase anonymous sign-ins would give guests a real `uid`. Linking an email on signup keeps the same `uid`, so no merge is needed. The costs are junk `auth.users` rows and less obvious RLS semantics. I rejected it for simplicity, but it's the strongest competing design. I'd like your view.
4. **Search quality.** Full-text search matches whole words, so "wirel" won't find "wireless" unless I add prefix matching (`:*`) in the query. With about 50 products, `ilike` plus the tsvector would both work. I'm not sure the GIN index is worth it at this size, but it's cheap and a good talking point.
5. **Denormalized ratings.** `rating_avg` and `rating_count` are computed by the seed script. This is fine while reviews are read-only. If reviews become writable, it needs a trigger.
6. **No `profiles` table.** Names live on addresses, and the email lives in `auth.users`. That's enough for the MVP, but a "Hello, Chand" header needs a name source.
7. **Stock is not reserved by the cart.** Two users can both have the last unit in their carts, and the second `place_order` fails with a clear error. That seems acceptable, but the UX for that error needs design.
8. **`order_items.user_id` duplicates `orders.user_id`.** I chose it for policy simplicity and speed. The cost is a theoretical inconsistency, which only the RPC writes, so it's controlled.
9. **`on delete set null` on `orders.user_id`.** It preserves orders if an account is deleted, but then no one can read them. I'm not sure that's the right call, and it may not matter for the assignment.

After applying any migration, I'd run the Supabase security advisors. I'd also test RLS with two accounts, since policy bugs are easy to write and easy to miss.
